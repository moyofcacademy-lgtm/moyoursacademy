# Architecture

## Framework notes (Next.js 16)

This project runs Next.js 16 — several conventions differ from older docs:

- `src/proxy.ts` replaces `middleware.ts` (same job: optimistic session check
  for `/admin/*`; every server action still re-checks with `auth()`).
- Request APIs (`params`, `searchParams`, `headers()`, `cookies()`) are
  async-only.
- Turbopack builds by default; `turbopack.root` is pinned in `next.config.ts`.

## Database

Prisma 7 with the `prisma-client` generator (output in `src/generated/prisma`,
gitignored, regenerated by `postinstall`). Prisma 7 removed `url` from the
schema datasource; the connection lives in `prisma.config.ts` and, at runtime,
in the driver adapter constructed in `src/lib/prisma.ts`:

- `DATABASE_URL` set → `@prisma/adapter-pg` (Neon/Supabase/any Postgres).
- Unset (local dev) → embedded PGlite database in `.pglite/`, bootstrapped by
  `scripts/db-setup.ts`, which applies the committed SQL migrations directly.

**PGlite supports exactly one process per data directory.** Concurrent access
corrupts it, and every later open fails with the WASM error
`Aborted(). Build with -sASSERTIONS for more info.` Two safeguards exist:

- `next build` prerenders with parallel workers, so `src/lib/prisma.ts` gives
  each build worker a throwaway temp **copy** of `.pglite/` (keyed off
  `NEXT_PHASE`), leaving the live directory untouched.
- Scripts (`db:setup`, `db:seed`, tests) still open the live directory — stop
  `next dev` before running them.

If the directory ever does get corrupted (e.g. a process was killed
mid-write), recovery is one command: `rm -rf .pglite && npm run db:setup` —
it's disposable seeded dev data.

Money is stored in **kobo as integers**. All datetimes are UTC in the
database and rendered in Africa/Lagos (WAT, fixed UTC+1) via `Intl`.

## Identity of an application

- **Reference** (`MOY-REF-XXXXXX`): issued when the guardian reaches the
  payment step (so the transfer narration can carry it) from an unambiguous
  alphabet (no 0/O/1/I); uniqueness re-checked in the submit transaction.
- **Member code** (`MOY-YYYY-XXXX`): minted **on acceptance** inside the
  accept transaction via `MemberCodeCounter` — an atomic per-year
  `INSERT … ON CONFLICT … RETURNING` upsert, so concurrent accepts can never
  produce duplicates. Idempotency comes from a status-guarded `updateMany`
  claim: only one accept can transition SUBMITTED/UNDER_REVIEW → ACCEPTED.
  `tests/member-code.test.ts` covers both properties.
- The `issueCodeOnSubmit` setting restores the original-spec behaviour
  (code at submission) if the academy insists — off by default because
  payment is verified manually.

## Uploads (Cloudinary)

Signed direct-to-Cloudinary uploads only — file bytes never touch the Next
server. `/api/uploads/signature` pins folder/type server-side per intent:

- `moyours/proofs/` — `type: authenticated`; viewable only through
  `/admin/registrations/[id]/proof`, which requires an admin session and
  redirects to a short-lived signed URL. Never publicly addressable.
- `crests/gallery/matches/news/players` — public; admin session required to
  obtain a signature. Deleting a club/album/asset destroys the Cloudinary
  asset by `publicId`.

After upload, the server re-verifies the asset (folder, format allowlist,
byte size) via the Admin API before accepting a submission; failures destroy
the asset. Without Cloudinary credentials, local dev uses a simulated
"dev-mock" upload path so the whole flow stays testable.

## Notifications

Everything goes through `src/lib/notify.ts`, which writes a
`NotificationLog` row for every send (SENT/FAILED/QUEUED — QUEUED when the
provider isn't configured). Failures never roll back business transactions;
the registration review page exposes a **Resend** button that rebuilds the
message from current DB state. SMS is Termii behind a provider interface
(`src/lib/sms.ts`) with one retry; emails are React Email templates in
`src/emails/` sent via Resend with plain-text fallbacks.

## Settings

Fees, bank details, training schedule, contact details, WhatsApp link,
subscription overdue day, and the member-code timing flag live in the
`Setting` table (key → JSON) with typed accessors and launch defaults in
`src/lib/settings.ts`. The enrollment and programs pages read from it, so
changing fees requires no deploy.

## Security posture

- Admin-only auth (NextAuth v5 credentials + bcrypt, JWT sessions, 12h);
  login rate-limited with lockout; proxy gates `/admin/*`; every action
  re-checks the session (`requireAdmin`).
- Zod validation server-side on every input; NG phone numbers normalized to
  E.164; child data minimized on public surfaces (status page returns first
  name + progress only, to holders of the reference or guardian phone).
- Rate limits (in-memory, single-instance): enroll 5/h/IP, signatures
  20/h/IP, status checks 20/h/IP, login 5/15min. Swap `src/lib/rate-limit.ts`
  for Redis when scaling out.
- Registrations are addressed by cuid ids in admin only; public lookups use
  the unguessable reference.
- Audit log records every admin mutation with actor, entity, metadata, IP.

## Data retention

Rejected applications keep their proof asset for 90 days for dispute
resolution, then should be purged (delete the registration in admin — proof
destruction is wired to deletion). Formalize the cadence with the academy.
